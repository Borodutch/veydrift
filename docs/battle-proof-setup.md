# Production setup requirements (inactive research)

Ticket #44 does not permit a single-process development Setup to become production key material. No production proving/verifying keys or ceremony artifacts are generated by current tests. Multiple calls to Setup or local processes controlled by the same operator do not constitute independent ceremony contributions.

## Available upstream mechanism

Pinned gnark v0.16.3 includes BN254 Groth16 MPC setup in `backend/groth16/bn254/mpcsetup`. Source inspection of `setup_test.go` demonstrates Phase1 initialization/contributions, serialized transcript verification via VerifyPhase1, circuit-specific Phase2 initialization/contributions, and VerifyPhase2 producing keys. `setup.go` specifies a beacon challenge observed after the latest contribution and reproducible sealing. These APIs are tools, not provenance for our circuits. Its test strings/local contributors are not production assurance.

PLONK intermediate circuits can derive keys from a sufficiently large reviewed universal KZG SRS. Validate curve, degree, powers, public contribution transcript and conversion; Ethereum BLS12-381 KZG data is not a drop-in BN254 SRS. A final BN254 Groth16 wrapper still needs circuit-specific setup. Library audits do not audit our statements, constraints, key binding, wrapper or deployment.

## Before activation

- Freeze circuit/source/dependency versions and canonical encodings; independently review constraints, recursion keys, transcript options and final verifier.
- Validate compatible phase-1/universal parameters at the required domain size. Record immutable hashes, contribution transcript, provenance and validation commands.
- Arrange genuinely independent contributors for necessary circuit-specific phases, with contribution verification and predetermined future beacon policy. Security requires an honest contribution with discarded entropy; running processes ourselves does not establish that.
- Verify entire transcripts, reproduce sealing/key derivation, compare circuit/key/verifier digests, generate/verify actual proofs natively and on the EVM, and freeze the approved verifier per battle.
- Document public proving-data availability and signer separation. Do not retain entropy/toxic waste or claim secure erasure merely from process exit.

These are activation prerequisites, not a reason to stop implementation/testing now. If contribution/provenance remains unavailable when activation is otherwise ready, leave activation off and report that concrete external prerequisite instead of using development keys.
