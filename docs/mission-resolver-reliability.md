# Mission resolver confirmation and archival retention

## Ordinary admission versus finality

The private resolver SQLite journal separates active/unproven intents (32) from canonically confirmed retained intents (4096). This is not a larger pending nonce window: an unresolved receipt, unknown send, prevented broadcast, outstanding signing reservation, or nonce contradiction still holds the shared signer. A prevented broadcast holds it only until the next pass proves it was never dispatched and retires it (see [locally prevented batches](./resolver-nonce-recovery.md#durable-mission-replay)); before that retirement existed, one quote that expired during a slow signing step held the signer indefinitely. Existing same-body chronology, fee caps, pre-sign readiness, identical-byte replay/backoff and cross-process send/lease fencing are unchanged.

Ordinary admission requires the original locally signed envelope and its durable reservation/result binding, the matching canonical receipt hash/from/to, canonical block identity, every member's block-pinned domain outcome, and a consumed signer nonce at that block bracketed by another canonical hash read. Existing signed but weakly hydrated rows must obtain that proof; old hash-only rows remain in the original bounded fail-closed path. A receipt can consume a nonce without completing a mission, including reverted and partial batches; admission never invents a terminal domain outcome.

The highest proven nonce's receipt is the durable canonical **frontier**. Every pass checks its containing hash and, until finalized, block-pinned consumed nonce. Before a successor is committed, the old frontier is checked again; the current frontier is checked at the end. Nonce/block ordering must be consistent. Thus a reorg of any historical ancestor necessarily changes the frontier hash, even if that ancestor is outside the current archive page. A crash cannot advance the persisted frontier before the old-anchor check. Once finalized, frontier checks need only the immutable header, not indefinitely retained historical state.

### Trust and reorg risk

This is a trusted, coherent canonical RPC model, not an independent-provider quorum or a claim of cryptographic ancestry proof from untrusted RPC responses. Canonical number-to-hash reads must represent one chain; locally signed transaction identity additionally binds chain and signer. A Byzantine RPC, corrupted trusted journal, or finalized-consensus violation is outside this model. A reorg immediately after a check remains possible, as for ordinary confirmed Ethereum submissions. Subsequent reconciliation fails closed before another allocation; signed bytes and outcomes remain retained until safe retirement. The indexer and canonical domain reads remain responsible for projection/reorg reconciliation; no balance credits are inferred from admission metadata.

Do not switch providers per request or select the highest reported finality. A replacement endpoint must preserve the frontier's chain/block identity. Automatic independent finality failover is deliberately not introduced: normal traffic no longer needs that liveness dependency, while receipt retirement still requires a coherent explicit finalized tag and matching canonical block hash. Node/reference disagreement belongs in the node monitor and release evidence. Multi-candidate legacy recovery is different: its initial original/alternative winner, reference verification and finality-based signer hold remain unchanged. Once that complete proof has durably finalized, the steady-state checks below replace repeated historical hydration.

## Reusing already-finalized recovery evidence

The post-finality path validates the persisted winner receipt against its exact finalized intent, membership, operation, chain/signer/nonce and candidate set. The original evidence-bearing recovery manifest must still reconstruct the same binding. Unknown signing reservations remain fenced. No winner, loser, fee, manifest or recovery-history row is rewritten by reuse.

Every admission then checks the current chain ID and consumed latest signer nonce (shared once per pass), candidate receipts and the persisted finalized containing-block hash. A contradictory winner receipt, changed canonical anchor, regressed nonce or second canonical candidate still fails closed. An explicit receipt-not-found can represent pruning: the unchanged finalized anchor plus the previously verified durable receipt remains authoritative; transport errors never count as absence. This follows the same coherent, non-Byzantine RPC/finality trust model described above. A finalized consensus violation or arbitrary journal tampering is not silently repaired.

The original full proof authenticated transaction bytes, block-pinned assets/domain outcomes, independent reference identity and finality. That immutable proof is reused, not re-established from current historical transaction/state/reference RPC on every tick. The usual two-candidate steady path takes three reads/group plus two shared identity reads, so 32 retained groups fit the existing 128-read budget without domain rehydration or repeated receipt telemetry. Conflicting orphan observations may cost extra reads and still respect the same deadline/budget. This is not a new finality assertion and does not weaken the provisional-winner hold or signing path.

After the node accepts a prepared batch (the broadcast returns its exact hash), the coordinator waits for its receipt (500 ms polling, 30 seconds) before the post-broadcast reconciliation pass. A just-sent envelope cannot have a receipt yet; reconciling immediately used to resend identical bytes twice within a second, exhaust the three-attempt replay budget and block admission for a soon-mined batch. The coordinator enforces the 30-second bound itself (`inclusionWaitMs`), so a caller `confirm` without a timeout cannot hold the signer lease; a late result from such a wait is never acted on. Every wait emits `resolver_inclusion_wait` with `outcome` (`included`, `timeout` or `error`, a fixed category and never the error text), `waitMs`, `timeoutMs`, the nonce and the public transaction hash, so production can confirm that accepted batches are included within the wait. A wait timeout or error only falls through to the unchanged reconciliation, which stays authoritative and replays identical bytes if inclusion never arrives; if the lease was lost during the wait, that pass fails closed without a resend or a new nonce. Transport errors, ambiguous responses and deterministic rejections are not acceptance and keep the immediate replay path.

Every reconciliation-pass `resolver_reconciliation_blocked` event carries the real sanitized error (`reason`, with signed bytes, hashes and URL paths/credentials redacted, plus `reasonCode` for typed readiness errors such as `pass-deadline` or `rpc-unavailable`), the pass `stage` that failed (`preflight`, `recovery`, `frontier`, `active`, `archive`, `final-frontier`; a frontier re-verification or nonce/block order contradiction found while proving an active row reports `frontier`) and `slowestReadMs`; the separate window-full event keeps its own fields. `reasonCode` is omitted for local backpressure that is not a proof rejection (an unresolved earlier read, a missing checkpoint reader, an exceeded retained window); the reason text names it. Retained recovery lineage, which stays in the journal even after it is finalized, is reported separately as `recoveryGroups`/`recoveryNote` and never replaces the reason. `slowestReadMs` is wall time and includes event-loop stalls while a read is in flight, so a deadline failure with a small `slowestReadMs` points at a writer stall between reads (for example a synchronous SQLite commit on a slow disk), while a large one means either a slow read or a stall during it.

A typed pre-allocation admission failure now has its own flat, one-resolution-interval cooldown. It never increments retry failure counts for the selected missions. Due queues remain visible, health remains degraded through the shared hold, and the next eligible retry includes the still-eligible candidates immediately after the gate recovers. Genuine per-mission failure/chronology exclusions keep their existing separate backoff. No shared failure clears those candidate-specific holds.

## Incremental archival work and storage

Each lease-fenced pass visits at most 32 active rows and eight retained confirmed rows, plus the constant-size frontier. A durable nonce cursor resumes archive pages after restart and wraps at the end; a one-row look-ahead distinguishes a full page from the end, and the cursor is written at most once per pass and not at all while a single page covers every retained row, because each FULL-synchronous commit can stall the writer's event loop on a contended disk. When a pass fails partway through a page, that one write records the last fully reconciled archive row (only while the process still owns the lease), so the next pass resumes after it instead of re-reading the earlier rows. Partial-index scans and LIMIT bound loaded rows; the original 128 asynchronous-read / 5-second pass budget, late-result fencing and outstanding-read tracking still apply. Pages do not authorize admission. Normal empty-queue batch ticks also reconcile.

An unavailable finalized tag retains records without treating latest as finalized. A contradictory finalized hash fails closed. A hung read still reaches the bounded pass deadline and is actionable, not silently ignored; persistent RPC transport failure is not promised uninterrupted service. Legacy unproven history may need multiple bounded drain passes before admission.

At explicit canonical finality, an ordinary row's signed blob and its transferred signing-result copy are cleared in the same fenced transaction; hashes, nonce, membership, outcomes and attempts remain. Recovery-group signed evidence is excluded. The append-only `resolver_transaction_audit` history (read by no admission, replay or recovery decision) is retained for 30 days; after a successful reconciliation the coordinator sweeps at most 5,000 of its own resolver's expired rows per minute in one short lease-fenced write, so the journal stops growing with lifetime traffic. Audit rows for an unfinalized intent nonce, an unresolved (`allocating`, `ambiguous`, `submitted`) attempt or any nonce-recovery lineage are never pruned; a monotonic sweep that reads at most one 5,000-sequence window per minute steps past them, and a new sweep from the start of the table begins daily (and after a restart), so rows whose evidence has since resolved become prunable. A failed prune is reported as `resolver_audit_prune_failed` and never blocks admission. SQLite reuses freed pages. There is no deletion of unfinalized intent evidence or automatic destructive VACUUM/reset. At 4096 retained confirmed intents, new prepared batches stop while reconciliation can drain them. At 240 MiB of live database pages (page count minus the reusable freelist) plus WAL, even new lease/cursor writes stop, reserving headroom for existing operations/late signer results. The one exception is retention: a reconciliation tick at the ceiling still runs the same throttled, bounded, evidence-guarded audit prune under a single-try lease (no reconciliation, cursor or admission work), and only while the journal is below a fixed 16 MiB reserve above the ceiling, so a journal filled by expired history can recover without a pinned WAL reader growing it without bound. Admission stays blocked until a later pass measures the journal under the ceiling. This is a safety ceiling, not unlimited lifetime storage: investigate pinned WAL readers/disk and plan reviewed private archival maintenance before reaching it. Never restore an old nonce journal or manually delete rows to clear admission.

## Health and operating targets

Writer mission-resolution health now includes admission active/retained counts and their limits, whether counts are capped, database-plus-WAL bytes, last canonical settlement time, and a fixed non-secret blocked reason. Admission blocking degrades health even when tick lastError or failure counters are zero. Existing due-arrival/return oldest ages, counts, completed legs and tick timings supply queue progress; public health does not contain signed bytes, memberships or upstream credential-bearing errors.

Targets for the existing deterministic monitor (no new model polling):

- Alert on any admission block persisting across two samples; dedupe by fixed reason and send a single recovery transition. The transient `canonical-reconciliation-required` and `shared-admission-block` reasons clear on the resolver's ~30s retry while missions keep settling, so they alert only after four consecutive samples (~20 minutes at the 300s cadence). `admission-transient-sustained` applies the same gate to a continuous block that alternates between the two reasons. Real stalls are caught by the due-queue impact alerts.
- Warn at 75% confirmed retention (3072) or 192 MiB journal+WAL, before the hard ceilings.
- Use existing mission promptness target for oldest due arrival/return. Escalate if a nonempty eligible queue makes no canonical settlement progress for 120 seconds, excluding documented game pause/dependency holds.
- Keep node latest/safe/finalized age and independent-reference disagreement separate from resolver health. A finality lag alone is not proof of a latest-head outage.
- Retain existing signer-balance/fee readiness alerts; no new signer, funding or fee-cap relaxation is introduced.

## Verification and release

The offline integration tests exercise 48 locally signed coordinator submissions and 40 full production batch selection/readiness/sign/send/receipt paths with finality frozen, including restart after 32. They assert bounded reconciliation reads, durable archive cursor movement, deep reorg and consumed-nonce failure, missing finality versus contradictory finality, retention admission stops and finality-safe compaction. Existing crash/persist/send, ambiguous transport, lease, two-second recovery readiness, chronology and domain accounting suites remain release gates. Post-finality regression tests also cover a 5.1-second historical transaction transport that is never touched by the reused proof, complete fresh batch readiness/sign/send after recovery, winner/chain/nonce/journal contradictions, conflicting candidates, explicit pruning versus transport failure, and 47 candidates recovering from repeated shared admission failures after 5 seconds rather than 300 seconds. Synthetic keys and transports never send to a live chain.

Release must retain one writer and the same private journal through the managed stop-first rollout. Back up consistently, verify current recovery owner and running SHA, and never overlap an operator recovery with deployment. The schema is additive but an old binary does not understand admission separation and will conservatively see retained rows as a full window; use hold-sends/forward repair rather than assuming a transparent downgrade. Dedicated QA and the release owner still owe sustained live queue drainage, real traffic, node/reference advancement and asset-accounting proof; offline tests alone do not complete ticket #61.

## Accepted but never included: same-nonce supersession (#397)

On 2026-11-02 resolver nonce 212987 was accepted by every Base endpoint (`already known`) but never included, and mission resolution stopped for more than an hour. The batch held one `Progress` battle leg, signed at the full 16,777,216 gas.

Base's builder (`base/base crates/builder`) checks each transaction's *metered execution time* against `max_execution_time_per_tx_us`. A refusal there is permanent for that hash, so the transaction stays in the mempool and identical-byte replay can never succeed. A fee bump on its own does not help either, because only less work does.

**Per-transaction work budget.** Staged combat commits as many 1M-gas stages as its envelope allows, so the signed gas limit is what bounds the work. Batches are now signed at `VEYDRIFT_MISSION_BATCH_WORK_GAS` instead of the full cap. It defaults to 2,500,000 and accepts values from 1,500,000 to 4,000,000; an invalid value is a config error.

**Hard work ceiling.** `VEYDRIFT_MISSION_BATCH_MAX_WORK_GAS` caps every automatically signed batch, escalation included. It defaults to 3,000,000, clearly below the ~4.2M of work Base refused, must be within 1,500,000..4,000,000 and at least the work budget (so the work budget is effectively at most 4,000,000 too); an invalid value is a config error. Nothing is ever signed above it (or above what the ETH cap affords). The 4,000,000 bound is also enforced wherever a budget or ceiling is read, not only by the env loader, so a policy built in code cannot exceed it either (#408). The single-call `resolveFleetMission` path (unbatched fallback) is signed at this same ceiling instead of the 16,777,216 block envelope.

Within those bounds:
- Every batch is first simulated exactly at the work budget, whatever the reference at the cap needed, and signed there if every leg is still `Settled` or `Progress`. A battle that would settle at the cap with more work than the budget therefore commits fewer stages (`Progress`) and continues next tick. Each leg runs in its own bounded delegatecall, so a leg short of gas returns `Failed`/`GasLimited`, never reverting the batch.
- A batch whose every leg is `Settled` did all its work inside the signed gas, so it must also keep the 20% safety margin over its measured need (intrinsic, forwarding loss and tail included) at the signed gas; otherwise a small state drift before inclusion could turn it into a paid no-op (#408). A leg making `Progress` uses whatever gas it gets and needs no such margin.
- Several legs that are not productive at the budget, or that all settle there without the margin, are split by packing (`BatchWorkBudgetError`, an unpaid unproductive exclusion; each leg is retried alone).
- A single leg that is not productive at the budget, or settles there without the margin, escalates gradually (2×, 4×, …, and its measured need + 20%) to the smallest productive envelope with the margin, never above the hard ceiling, with a `mission_batch_work_budget_exceeded` warning.
- A leg that settles thin and whose need + 20% is above the ceiling (a staged battle's final segment) is simulated once more below its lightest thin settlement by the missing margin (never under 1,500,000), where a staged battle makes `Progress` with one stage fewer.
- A single leg that is not productive (or not with the margin) even at the ceiling is excluded as an indivisible blocker (`BatchWorkCeilingError`, the existing `mission_batch_indivisible_blocker` alert) and is never signed: one stuck mission instead of a wedged signer. When the ceiling is lower than the work ceiling only because the ETH cap affords less gas at current fees, the exclusion is a plain `BatchCapacityError` instead. It raises the same `mission_batch_indivisible_blocker` alert as every fee-cap exclusion, but the reason names the ETH cap rather than the work ceiling.

On mainnet, the stuck leg (mission 109746, arrival) did 1.27M gas of work (`Progress`) at the budget, against 4.21M at the cap; at 1.5M it fails.

**When supersession triggers.** A durable batch intent qualifies when all of the following hold:
- Its sends were accepted or ambiguous (`replay_state = retryable`).
- It has been sent `supersedeAfterAttempts` times (default 6). After the third send, retries are 60 s apart, so this also means at least three minutes without inclusion.
- The signer's latest nonce still equals the intent's nonce.
- No other journal intent exists at or after that nonce, and the nonce has no recovery lineage.

Instead of sending identical bytes again, the coordinator plans **at most one alternative at the same nonce**:
- It keeps the same chain, target, calldata and membership.
- Its signed gas is the work budget, which must be strictly below the original's.
- An exact simulation at the same block must show at least 10% less execution work than the original envelope.
- Both fee fields are raised by at least 25% (Base's replacement rule needs 10%) and at least to the current quote.
- It passes the unchanged exact-envelope replay preflight before signing and again before its first send. That covers fee freshness, the per-transaction 0.0002 ETH ceiling and the batch budget, and a productive simulation.

**Planning budget.** Planning makes about a dozen sequential reads, two of them heavy exact `eth_call`s (about 0.9 s against a public Base RPC on 2026-11-02, for nonce 212987). It gets its own bounded budget (`supersessionPlanningMs`, default 20 s): the reconciliation pass deadline is extended once by it plus a full ordinary pass budget, and planning is raced against the planning budget alone. A planner that overruns therefore always leaves time for the unchanged identical-byte resend in the same pass. Nothing is reserved or signed before planning returns, so a planning timeout, a stale quote, a fee-cap or transport error, or a quote that expires just before the reservation is reported as unavailable (below), never as a failed pass. Only a lost lease or the (extended) pass deadline fails the pass.

If the alternative cannot do less work (for example an original already within the budget, a batch with no staged leg, or a first stage that does not fit), the planner raises `SupersessionUnavailableError`. The same applies to any out-of-bounds plan, a moved nonce or a non-exclusive journal. In all these cases nothing is reserved or signed: `resolver_same_nonce_supersession_unavailable` is emitted and the original keeps its unchanged identical-byte resends, since it may only have been dropped from the mempool. If Base never includes it, an operator has to review it. No fresh nonce is allocated and no evidence is deleted. The plan is retried on every pass (the state may change), but the warning is emitted once per envelope and reason, again at once when the reason changes, and otherwise at most hourly while it persists (#408).

**Signing.** Signing follows the existing reservation fence:
1. A `supersede:` reservation is committed after the final guard. The signer is then invoked with no await in between.
2. The signed result is inserted as append-only evidence.
3. One lease-fenced transaction inserts the alternative (`supersedes = <original hash>`) and transfers the reservation.

These three commits use NORMAL sync, because the send fence's FULL commit makes them durable before any broadcast. After a crash between steps 2 and 3, the next pass resumes the transfer from the retained result and never signs again.

A reservation without a result stays fenced (`signing result unknown`) and blocks every pass. The alternative can only be broadcast from its transferred row, so such a reservation was provably never dispatched. Even so, clearing it is a manual, reviewed journal repair: stop the writer, back up the journal, mark that one reservation transferred and add an audit note. Never re-sign.

**Reconciling the pair.** While both candidates are pending:
- Each pass reads both receipts and reuses them for the winner.
- Only the alternative is resent (identical bytes, the normal backoff). The original is never resent.
- An alternative is never superseded again.

The candidate whose canonical receipt proves the consumed nonce (or is finalized) wins. In the same transaction that persists its receipt, the other candidate becomes `superseded`. Its signed bytes, its row and its audit history are retained, and it no longer counts toward admission, audit-prune holds or legacy-recovery exclusivity. Two canonical candidates fail closed and keep both envelopes. An alternative that is itself sent `supersedeAfterAttempts` times without inclusion emits `resolver_same_nonce_alternative_not_included` (once, then at most hourly while it persists): it is never superseded again, so that needs operator review.

A reorg that drops the winner and mines the retired candidate fails the frontier check closed. The retired row is then excluded from automatic reconciliation, and an operator must repair it. Audit rows `superseding`, `superseding-candidate` and `superseded` record the lineage, together with the events `resolver_same_nonce_supersession` and `resolver_same_nonce_candidate_retired`.

**Rollback.** An older binary does not understand `supersedes` or `superseded`. It treats a `superseded` row as unresolved and blocks admission permanently once any supersession has happened, not only while a pair is unresolved. Roll forward; never downgrade past this release.
